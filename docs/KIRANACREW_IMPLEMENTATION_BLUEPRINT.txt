4. NammaOps MCP integration code
I recommend a dedicated Node.js backend service.

Install:
npm install @modelcontextprotocol/sdk zod dotenv


The following is the integration pattern. It is a starting implementation, not a complete drop-in replacement for your existing Agent Town gateway.

integrations/erpnext/mcp-client.ts

import "dotenv/config";

import {
  Client
} from "@modelcontextprotocol/sdk/client/index.js";

import {
  StdioClientTransport
} from "@modelcontextprotocol/sdk/client/stdio.js";

const transport = new StdioClientTransport({
  command: "npx",
  args: [
    "-y",
    "@hvgllc/hvgerp-mcp",
    "--categories=sales,inventory,purchasing,accounting"
  ],
  env: {
    ...process.env,
    ERPNEXT_URL: process.env.ERPNEXT_URL!,
    ERPNEXT_API_KEY: process.env.ERPNEXT_API_KEY!,
    ERPNEXT_API_SECRET: process.env.ERPNEXT_API_SECRET!
  }
});

export const erpClient = new Client({
  name: "nammaops-gateway",
  version: "1.0.0"
});

export async function connectERP() {
  await erpClient.connect(transport);

  const result = await erpClient.listTools();

  console.log(
    "ERPNext MCP connected",
    result.tools.map(tool => tool.name)
  );

  return result.tools;
}

export async function callERPTool(
  name: string,
  args: Record<string, unknown>
) {
  return erpClient.callTool({
    name,
    arguments: args
  });
}



This lets your existing orchestration backend discover and invoke ERPNext MCP tools.

For production, add timeouts, error classification, input validation, retry rules for safe reads, and a controlled shutdown handler.
5. Agent definitions and permissions
This is one of the most important design decisions.

Do not let every agent access every ERPNext operation.

Give each agent a restricted set of tools and responsibilities.
Agent 1 – Inventory Agent









Purpose: Understand the current stock situation.
Read-only


Allowed MCP capabilities:
- Item list.
- Stock balance.
- Warehouse list.
- Stock ledger.
- Product details.
Forbidden:
- Deleting products.
- Changing stock quantities.
- Submitting stock adjustments.
- Creating purchase orders.
Example system instruction:
You are the NammaOps Inventory Agent.

Your responsibility is to inspect inventory.

1. Read product stock balances.
2. Compare stock against configured reorder levels.
3. Identify low-stock and expiry-risk products.
4. Report quantities and warehouse locations.
5. Never modify inventory directly.
6. Never invent stock quantities.
7. Report unavailable data explicitly.

Return structured results to the Manager Agent.


Agent 2 – Sales Agent









Purpose: Understand sales performance.
Read-only


Allowed:
- Sales invoice list.
- POS invoice list.
- Customer list.
- Sales reports.
- Product sales analysis.
Example output:

  "total_sales": 8500,

  "top_products": [
    "Milk",
    "Rice",

Use real ERPNext results in the application; this JSON is illustrative.
Agent 3 – Procurement Agent









Purpose: Prepare purchase recommendations.
Approval required


Allowed:
- Read supplier list.
- Read supplier quotations.
- Read item prices.
- Create draft purchase orders.
Restricted:
- Submit purchase orders.
- Create purchase receipts.
- Cancel purchase documents.
The agent can prepare an order but cannot finalise it without owner approval.
Agent 4 – Finance Agent









Purpose: Produce business summaries.
Read-only


Allowed:
- Sales summaries.
- Purchase invoice reports.
- General ledger reports.
- Profit and loss reports.
- Payment summaries.
Do not calculate profit by simply subtracting purchase orders from sales. Use posted accounting records and an appropriate accounting report.
Agent 5 – Manager Agent









Purpose: Coordinate the workforce.
Orchestrator


Responsibilities:
- Understand owner intent.
- Delegate tasks.
- Combine agent results.
- Detect inconsistent reports.
- Request owner approval.
- Generate the final spoken response.
The Manager should not have unrestricted access to ERPNext either. It should only invoke explicitly approved workflow operations.
Permission matrix

C. Create stock intelligence workflow
backend/workflows/stock-intelligence.ts

type StockItem = {
  name: string;
  available: number;
  reorderLevel: number;
};

export function analyseStock(items: StockItem[]) {
  const lowStock = items.filter(
    item => item.available <= item.reorderLevel
  );

  return {
    totalProducts: items.length,
    lowStockCount: lowStock.length,
    lowStockItems: lowStock.map(item => ({
      product: item.name,
      available: item.available,
      reorderLevel: item.reorderLevel,
      shortage: Math.max(
        0,
        item.reorderLevel - item.available
      )
    }))
  };
}



The inventory data must be fetched from ERPNext first. This function only performs deterministic calculations on the returned values.
D. Build purchase approval
backend/services/approvals.ts

type Approval = {
  id: string;
  action: "submit_purchase_order";
  documentName: string;
  status: "pending" | "approved" | "rejected";
  approvedBy?: string;
  createdAt: string;
};

const approvals = new Map<string, Approval>();

export function requestPurchaseApproval(
  documentName: string
) {
  const approval: Approval = {
    id: crypto.randomUUID(),
    action: "submit_purchase_order",
    documentName,
    status: "pending",
    createdAt: new Date().toISOString()
  };

  approvals.set(approval.id, approval);
  return approval;
}

export function approvePurchase(
  id: string,
  ownerId: string
) {
  const approval = approvals.get(id);

  if (!approval || approval.status !== "pending") {
    throw new Error("Invalid approval request");
  }

  approval.status = "approved";
  approval.approvedBy = ownerId;

  return approval;
}



This is a prototype in-memory example. For the real application, persist approval records in your database, bind approval to the exact document and amount, expire old approvals, and make submission idempotent.

Never let the LLM call the purchase-submit tool just because the owner said something vaguely affirmative. Bind approval to a specific purchase order, total and supplier, then verify it on the server.

14. Important technical decisions
A few things I would insist on:
1. Keep ERPNext as the single source of truth for business records.
2. Keep your existing Agent Town orchestration instead of rebuilding it.
3. Use the existing MCP server as the ERP integration, with a separate NammaOps permission gateway.
4. Do not give agents unrestricted ERPNext write access.
5. Store approvals and audit events in your application database.
6. Use synthetic data for the hackathon.
7. Never expose Gnani or ERPNext credentials to the frontend.
8. Treat the Docker demo as disposable; use a persistent controlled instance for the final public demonstration.
One particularly important MCP detail: the current hvgerp-mcp repository supports many operations, including generic DocType CRUD and purchase-order submission. That power is useful, but it also makes permission filtering essential.
